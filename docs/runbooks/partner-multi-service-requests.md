# Multi-service partner requests

New requests require `PARTNER_MULTI_SERVICE_REQUESTS_ENABLED=true` and the existing portal write flag. `PARTNER_MULTI_SERVICE_ACCOUNT_IDS` can narrow the initial cohort. Existing saved requests remain readable if the new-request gate is paused.

Apply additive migration 0176 before deploying consumers that read the new fields; deploy API and readers before enabling the new-request flag. Historical bookings retain their appointment and pricing. Model 2 parents have no appointment: service lines preserve submitted scope and rate evidence, while real scheduled visits own appointments. Migration 0177 separately adds owner alert stages.

Rates are display evidence. Staff confirms each service amount. Explicit staff quantities are checked against the request’s applicable saved rates; portal requests never calculate estimates. Pricing uses the previously priced snapshot first, then submitted rates, and fills only missing service variants from a newer publication. Pricing snapshots record `rateSources` for each rate and `minimumRateCardVersionId` for the company minimum; that submitted minimum is retained even when the service had no rates yet. Staff review, charge validation, and new visits all use this same applicable snapshot. Publishing a newer card never changes an already saved rate or visit minimum. Later pricing writes a separate rate snapshot and preserves the submitted snapshot. Missing rates and missing requested variants block pricing and scheduling. Each visit has one captured minimum. Adding a visit that exceeds the already confirmed total fails without creating an appointment; staff must explicitly revise the price.

`partner-multi-service.ts` is a `capacity_locked` schedule writer. Creation and rescheduling share `createPartnerMultiServiceVisit`; it acquires the parent financial advisory lock and parent row lock, then the global schedule lock, before checking pool and named-resource capacity and writing the appointment. It charges capacity once for a visit, merges compatible service requirements, and never copies the parent monetary total into visits. Rescheduling updates the same visit and appointment, excluding their previous capacity. Visit completion/cancellation uses the same lock order. Whole-request cancellation is called while the caller holds the parent financial/mutation lock; the helper acquires the global schedule lock before releasing any visit capacity.

Staff mutation routes use the existing authenticated mutation boundary, mandatory expected version, idempotency claims, and a co-committed audit receipt. Visit, mapping, appointment, parent, audit, idempotency receipt and calendar-outbox writes commit together. No provider call happens inside these transactions. Completion resolves explicit service lines and never completes a line that still has another open visit. Parent completion requires all lines and visits to be resolved and the existing completion-proof policy to pass.

The accepted-price bridge remains a financial metadata writer: `lockPartnerRequestFinancials` resolves the existing appointment collection lock for historical bookings and the parent collection lock for model 2. Neither branch changes scheduling or finalized revenue.

Migration 0178 enforces owner-stage identity; 0179 adds visit-bound preferred-date requests and `partially_scheduled`. Migration 0180 extends refund-allocation ownership to the commercial parent while preserving historical appointment binding. Apply through 0180 before any new consumer is deployed. Scheduling coverage includes only active scheduled/in-progress visits: a finished visit does not cover a service that still needs work. The reader exposes uncovered service line IDs, including on an in-progress parent.

Portal date changes use `POST /api/portal/v2/jobs/:jobId/visits/:visitId/reschedule`, the parent strong ETag, and an idempotency key. The body contains one to three `preferredWindows` entries. The receipt says `mode: review` and `consequence.existingScheduleRemainsInPlace: true`; it does not reschedule anything. One pending date request per parent is supported. Staff decisions retain the selected visit's services, duration, and captured minimum and reserve its new time atomically through the same capacity writer. Decline or withdrawal leaves the schedule intact. Whole-parent legacy reschedule APIs direct model 2 callers to choose a visit.

Explicit service-line before/after proof minima are checked before that service can complete, counting ready shared evidence or evidence assigned to that line. Evidence assigned only to another service does not count. The existing account/job proof policy still governs final completion.

Bulk CSV supports `request_group` to combine service rows into one request, or `service_lines` for a bounded JSON array with each service's scope. Every grouped row must agree on property, contact, dates, instructions, proof defaults, and billing references. Group validation fails together before request writes. Worker claims and outcome writes update the whole group; its deterministic draft/submission identity prevents duplicate parents on retry. Legacy quantity columns are rejected for groups to avoid discarding service-specific measurements. Templates/book-again/recurring reuse service scope, clear photo associations, and obtain fresh submission rates, pricing, approvals, and visit scheduling.

Canceled-visit calendar deletion uses a dedicated immutable authorization receipt tied to the successful staff/partner cancellation audit, account, parent, visit, appointment version, and prior calendar event. The worker verifies this receipt before deletion; generic cancellation authorization is unchanged. Generic appointment status updates cannot reopen a closed visit.

Validate this contract with `src/__tests__/partner-multi-service.test.ts` and `src/__tests__/partner-multi-service.postgres.integration.test.ts` in the API package. The database regressions submit against card A, publish B before pricing and C before scheduling, and require the original amounts and minimum to remain unchanged. Separate cases cover partial variants, a saved card with no rates for the selected service, and no submitted card. They also assert that submitted JSON remains unchanged and that composed pricing retains each source version. Run the full database gate with `NODE_ENV=test DOTENV_CONFIG_PATH=/dev/null DATABASE_SSL=false pnpm test:partner-portal:postgres` and an explicitly configured disposable local `DATABASE_URL`; its startup guard rejects nonlocal and non-test database names. Serialize this gate with browser rehearsals sharing the same database.
